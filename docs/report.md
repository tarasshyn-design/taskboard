 Контрольні запитання та відповіді

1. Для чого потрібен локальний вебсервер (наприклад, Live Server) під час розробки?
Локальний вебсервер обслуговує файли проєкту через протокол `http://` (наприклад, `127.0.0.1:5500`), що ближче до реальних умов роботи сайту в мережі, дозволяє відстежувати HTTP-запити та коди стану в DevTools, а також автоматично оновлює сторінку в браузері після збереження змін у коді.

 2. Що означають коди стану HTTP `200`, `304` та `404`?
- `200` (OK) — запит успішно оброблено, ресурс знайдено та передано клієнту.
- `304` (Not Modified) — ресурс не змінювався з моменту попереднього запиту, тому браузер може використати закешовану копію.
- `404` (Not Found) — запитаний файл або ресурс за вказаним шляхом не знайдено на сервері (наприклад, при зміні шляху з `images/logo.png` на `images/logo1.png`).

 3. Яку роль виконує атрибут `alt` у тегу `<img>`?
Атрибут `alt` задає альтернативний текстовий опис зображення: він відображається замість картинки, якщо файл не завантажився (наприклад, при помилці `404`), а також використовується екранними читачами та пошуковими системами.

 Відповіді на запитання (Лабораторна 4)

1. Що змінилося у виводі `git status` після `git add`?
   Зміни перемістилися з невідстежуваних (`Untracked`) або неідексованих (`Changes not staged for commit`) до списку підготовлених до коміту (`Changes to be committed`), підсвіченого зеленим.

2. Що показує `git diff`?
   Команда показує построкові відмінності між робочим каталогом та індексом/останнім комітом: додані рядки позначені `+`, видалені — `-`.

3. Чим відрізняється `git switch main` від `git merge`?
   `git switch main` перемикає поточну гілку на `main`, а `git merge` об'єднує зміни з вказаної гілки в поточну активну гілку.

4. Чому виник конфлікт і як ти його розв'язав?
   Конфлікт виник через те, що в гілках `ukr-title` та `main` був змінений один і той самий рядок `<h1>` у `index.html`. Я відкрив файл, видалив службові маркери конфлікту та зайві дублікати, залишив об'єднаний заголовок і зафіксував злиття комітом.

1. Для чого потрібен файл `.gitignore` та чи видаляє він уже закомічені файли?
   Файл `.gitignore` вказує Git, які файли та папки (наприклад, віртуальні середовища `venv/`, кеш `__pycache__/`, секрети `.env`, системні файли `Thumbs.db`, `.DS_Store`) не потрібно відстежувати та додавати до репозиторію. Сам по собі `.gitignore` не видаляє файли, які вже були закомічені раніше — для їх видалення з індексу репозиторію потрібно використати `git rm --cached <файл>`.

2. У чому різниця між `git mv` та звичайним переміщенням файлу у провіднику?
   Команда `git mv` одночасно переміщує (або перейменовує) файл у файловій системі та одразу фіксує цю зміну в індексі Git (staging area), зберігаючи історію переміщення файлу для наступного коміту. При звичайному переміщенні у провіднику Git бачить видалення старого файлу та появу нового невідстежуваного файлу, які потрібно окремо додавати через `git add`.

3. Що таке GitHub Pages і які обмеження він має?
   GitHub Pages — це безкоштовний хостинг статичних вебсайтів безпосередньо з репозиторію GitHub. Його головне обмеження в тому, що він підтримує лише статичні файли (HTML, CSS, JavaScript, зображення) і не виконує серверний код (Python/Flask, PHP, Node.js тощо) та не працює напряму з серверними базами даних.

4. Навіщо використовувати гілки та Pull Request замість прямих комітів у `main`?
   Робота в окремих гілках дозволяє ізольовано розробляти нові функції чи виправлення, не ламаючи стабільну робочу версію проєкту у гілці `main` (з якої, зокрема, розгортається сайт). Pull Request забезпечує перевірку коду (code review), обговорення змін та безпечне злиття перевіреного коду в основну гілку.
